# 기술적 결정

이 문서는 채택한 MVP 결정과 그 이유를 기록한다. 포트폴리오의 범위를 넓히기 위해 추가한 기술 목록이 아니다.

## D-001 — 장소 선택, 순위 계산, 경로 생성을 LLM 외부에 둔다

**상태:** 채택.

OpenAI 사용 범위는 자연어 취향 Parsing, 선택적인 Tag 정규화, 이미 확인된 사실을 바탕으로 한 선택적인 최종 문장 작성으로 제한한다. Provider Adapter가 장소를 제공하고 애플리케이션 코드가 점수, 거리, 경로를 계산한다.

**이유:** 언어 모델은 장소의 실재 여부, 좌표, 영업 여부, 비용, 혼잡도를 확정할 수 없다. 결정론적 코드는 재현 가능한 Test, 비용 제어, 제약조건 검증, UI가 설명할 수 있는 점수 추적 기록을 제공한다. Parsing 호출 한 번과 최대 한 번의 설명 호출만 허용해 후보 반복문 안에서 LLM을 호출하지 않는다.

## D-002 — Next.js 프런트엔드와 단일 NestJS API를 사용한다

**상태:** 채택.

프런트엔드와 백엔드는 별도 Directory에 있지만 Microservice로 분리하지 않는다.

**이유:** UI와 추천 Domain은 경계가 분명하고 빌드 관심사가 독립적이다. 동시에 단일 백엔드 Process는 일정 생성 Transaction, Adapter 조정, 로컬 실행을 단순하게 유지한다. 현재 MVP에는 Service Discovery, Queue, Distributed Transaction을 정당화할 확장성 근거가 없다.

## D-003 — PostgreSQL, PostGIS, TypeORM Migration을 사용한다

**상태:** 채택.

**이유:** 여행, 경유지, 취향, 점수 Snapshot은 관계형 구조와 Transaction이 필요하다. 후보 거리·지역 Query에는 지리공간 Type과 Index가 필요하며, PostGIS를 사용하면 별도 Datastore 없이 이를 추가할 수 있다. TypeORM은 NestJS/TypeScript Stack과 잘 맞지만 Schema 변경은 명시적인 Migration으로 유지한다. 검토되지 않은 Schema 변경을 막기 위해 Runtime Synchronization은 비활성화한다.

## D-004 — MVP에 Elasticsearch를 추가하지 않는다

**상태:** 채택.

Provider 검색이 장소 탐색을 담당하고 PostgreSQL이 영속 데이터의 Filtering과 공간 Query를 담당한다.

**이유:** 초기 제품은 서울만 지원하고 별도 검색 Cluster의 필요성을 입증할 자체 Corpus나 Query 양이 아직 없다. Elasticsearch는 핵심 추천 가치를 개선하기 전에 동기화, 운영, 장애 유형을 추가한다. 검색 품질이나 규모 한계가 측정된 뒤에만 재검토한다.

## D-005 — 외부 서비스를 작은 Live/Mock Adapter 뒤에 둔다

**상태:** 채택.

장소, 혼잡도, 취향 Parsing은 명시적인 `mock`·`live` 모드를 가진 `PlaceProvider`, `CrowdProvider`, `TripPreferenceParser` Contract를 사용한다.

**이유:** 로컬 개발과 CI는 Credential 없이 실행할 수 있어야 하며 Domain 코드는 Vendor Payload 구조에 따라 분기하면 안 된다. 결정론적 Fixture는 순위·경로 Test도 안정적으로 만든다. Live 실패 시 조용히 Mock으로 전환하면 개발용 합성 데이터를 외부 결과로 위장하게 되므로 절대 그렇게 하지 않는다. Provider 모드와 경고는 Client에 반환한다.

## D-006 — 정규화된 장소와 Provider 원본 Snapshot을 분리해 저장한다

**상태:** 채택.

**이유:** 표준 Field는 점수 계산과 Query를 예측 가능하게 만든다. 원본 Snapshot은 출처를 보존하며 상위 시스템의 형식이 바뀔 때 Normalizer를 Debug할 수 있게 한다. 둘을 합치면 Provider 구조가 Domain 전체로 새거나 감사 근거를 잃게 된다. 외부에 없는 Field는 null로 유지하며, Snapshot이 표준값 추론을 허용하는 근거는 아니다.

## D-007 — 서울 혼잡도 데이터를 장소 내부가 아닌 지역 맥락으로 취급한다

**상태:** 채택.

**이유:** 성수역 일대 같은 지역의 관측값은 특정 카페 내부를 측정한 것이 아니다. 둘을 같은 값으로 다루면 정밀해 보이지만 거짓인 추천 근거가 된다. 따라서 혼잡도 맥락에는 `scope: area`, 지역 식별자, 관측 시간, 출처를 포함한다. 없거나 오래된 값은 알 수 없음으로 유지하고 이를 공개한다.

## D-008 — 일본 공개 시장 데이터는 Cold-start Prior로만 사용한다

**상태:** 채택.

취향 우선순위는 직접 입력, 관측된 행동, 집계 시장 Prior 순이다.

**이유:** 집계 조사는 Michi에 행동 데이터가 쌓이기 전 기본값을 개선할 수 있지만 개인을 설명하지 않으며 여행자를 고정관념으로 판단해서는 안 된다. 모든 지표에는 출처 URL과 수집 Metadata가 필요하다. Prior는 현재 요청에서 사용자가 직접 말한 내용을 덮어쓸 수 없다.

## D-009 — 동적 가중치를 지원하는 설정 가능한 결정론적 점수를 사용한다

**상태:** 채택.

기본 가중치는 버전이 있는 설정이다. 검증된 직접 신호에 따라 가중치를 조정한 뒤 정규화하고 항목별 점수와 함께 저장한다.

**이유:** 하나의 영구적인 가중치 Vector는 아직 측정하지 않은 제품 지식이 있는 것처럼 오해하게 한다. 동적 규칙을 사용하면 순위 계산을 LLM에 맡기지 않고도 혼잡 회피 같은 강한 요청을 반영할 수 있다. 가중치와 항목별 점수를 저장하면 `なぜここがおすすめ？`에 답할 수 있고 향후 Offline 평가도 가능하다.

## D-010 — 결정론적 경로 Heuristic으로 시작한다

**상태:** 채택.

구현된 Optimizer는 순위가 가장 높은 후보에서 시작해 남은 후보 중 가장 가까운 곳을 반복해서 선택하고, 도보 시간을 추정해 Timeline을 계산한다. 요청한 종료 시간이나 확인된 예산을 초과하는 경유지는 건너뛴다.

**이유:** 초기 데이터 규모와 학습 결과의 부재를 고려하면 ML이나 복잡한 Solver를 도입할 근거가 없다. Test를 거친 Heuristic은 이해하기 쉽고 제품을 검증하기에 충분하다. 거리는 지리공간 방식으로 계산하며 이동 시간은 길찾기 Adapter를 구현하기 전까지 고정된 도보 추정값이다. 현재 Engine은 확인된 영업시간이 있으면 이를 사용하고, 식사·카테고리 효용 규칙과 최종 Validator를 적용한다. Provider 길찾기와 전역 최적 경로는 이후로 미룬다. 최적화에는 LLM이 참여하지 않는다.

## D-011 — 빈 값을 채우지 않고 불확실성을 표현한다

**상태:** 채택.

알 수 없는 영업시간, 비용, 이미지, 좌표, 혼잡도 관측값은 null 또는 없는 상태로 유지한다. 확인된 제약조건 위반은 장소를 제외하며, 알 수 없는 제약조건에는 정책으로 정의한 점수와 경고를 생성한다. 좌표가 없는 후보는 반환된 경우 출처 추적을 위해 저장하지만 순위·경로 계산 전에는 제외한다.

**이유:** 알 수 없는 값을 영업 중, 저렴함, 한산함으로 취급하면 핵심 신뢰 모델을 위반한다. 불확실성을 공개해도 경로는 유용할 수 있지만 UI는 알 수 없는 값을 구분해야 한다. 선택된 비용 중 하나라도 알 수 없으면 총 예상 비용은 null이다.

## D-012 — MVP에서는 현재 추천 결과 하나만 유지한다

**상태:** 현재 MVP에서 채택했으며 결과 이력은 이후로 미룬다.

현재 각 여행에는 Algorithm 버전, 최종 가중치, 후보 수, 후보 점수를 포함한 추천 결과 하나가 있다. 경유지는 선택된 점수·혼잡도 Snapshot을 보관한다. 수정 작업은 현재 여행 경로에 적용된다.

**이유:** 버전 이력 모델은 향후 Offline 평가에 유용하지만 핵심 흐름을 검증하기 전에 활성 버전 제약조건과 더 복잡한 수정 의미를 추가한다. MVP는 설명에 필요한 현재 실행 상세 정보를 충분히 보존한다. 과거 추천 결과 버전은 행동·평가 작업을 시작할 때 추가해야 하며, 현재 Schema가 이미 지원하는 것처럼 표현하지 않고 기술 부채로 기록한다.

## D-013 — 일정 Field에는 서울 현지 날짜·시간을, 감사 기록에는 UTC를 사용한다

**상태:** 채택.

**이유:** 여행 일정은 서울 영업시간을 기준으로 하며 일본 Browser나 Server가 직렬화할 때 시간이 바뀌면 안 된다. 따라서 `travelDate`와 `HH:mm` 값은 `Asia/Seoul`을 의미하고, 조회·생성·관측 Timestamp는 UTC 시점이다. MVP는 시작 시간보다 이른 종료 시간을 조용히 익일 경로로 해석하지 않는다.

## D-014 — Core 완료 후 Log Friends와 영수증 기반을 진행한다

**상태:** 채택했으며 Core 검증 통과 후 실행했다.

**이유:** 행동 계측과 영수증 평가는 정상 작동하는 요청→경로 Loop가 있을 때만 가치가 있다. Core Lint, Test, Build, Database, API Smoke Test를 통과한 뒤 Phase 2에서는 범위를 제한한 기반만 추가했다. 명시적으로 활성화하는 안전한 이벤트 SDK·프런트엔드 이벤트와 영수증 Schema·민감정보 제거·Mock 후보 코드를 구현했다. 동기식 Planner 범위를 넓히지 않기 위해 이벤트 수집, Live OCR, 업로드·영속화 Workflow, 추천 Feedback은 이후로 미룬다.
