# 경로 최적화기

`HeuristicRouteOptimizer`는 Process 내부에서 동작하는 결정론적 Heuristic이다. 순위가 계산된 후보를 입력으로 사용하며 LLM이나 길찾기 API를 호출하지 않는다.

## 생성 알고리즘

1. 검증된 좌표가 없는 후보와 중복된 장소 ID를 제거한다.
2. 각 단계에서 현재 방문 가능한 모든 잔여 후보의 일정을 계산한다.
3. Haversine 공식을 사용해 시속 4.5km의 직선 이동 시간을 추정하며 최소 이동 시간은 5분이다.
4. 음식점은 점심(`11:30–14:00`) 또는 저녁(`17:30–20:00`) 시간에 맞추고, 원본 고기 카테고리는 저녁을 우선한다.
5. Provider가 제공한 영업시간 범위가 있으면 영업 시작까지 기다리거나 영업 종료 전에 방문을 마칠 수 없는 후보를 거부한다.
6. 요청한 여행 종료 시간 이후에 끝나거나 확인된 비용이 남은 확인 예산을 초과하는 후보를 거부한다.
7. 효용이 가장 높은 후보를 선택한다. 추천 총점 45%, 근접성 30%, 새 카테고리 다양성 15%, 식사 시간 10%다.
8. 방문 가능한 후보가 없을 때까지 반복한 뒤 전체 경로를 검증한다.

기본 체류 시간은 결정론적인 제품 가정이다. 공원·문화·음식점은 75분, 쇼핑은 50분, 그 밖의 장소는 60분이다. Provider가 제공한 사실이 아니다.

## 제약조건 검증기

`RouteConstraintValidator`는 다음을 확인한다.

- 유효한 당일 여행 시간 범위
- 1부터 연속되는 순서와 중복 장소 없음
- 여행 시간 범위 안에 있고 서로 겹치지 않는 경유지
- 일정에 배정된 시간이 `estimatedStayMinutes`와 일치하는지 여부
- 확인된 비용 합계가 예산을 초과하지 않는지 여부
- 존재하는 경우 Provider가 제공한 영업시간

비용이나 영업시간을 알 수 없으면 값을 만들어내지 않고 경고를 생성한다. 선택된 장소 중 비용을 알 수 없는 곳이 하나라도 있으면 `estimatedTotalCost`는 null이다.

## 수정 동작

삭제, 순서 변경, 재계산은 모두 `preserveOrder: true`로 같은 Optimizer를 사용한다. 백엔드는 제안된 순서대로 이동·방문 시간을 다시 계산하며, 남은 모든 경유지를 배치할 수 없으면 전체 수정을 `EDIT_ROUTE_INFEASIBLE`로 거부한다. 수정에 성공하면 하나의 Transaction에서 경유지와 여행 상태를 `modified`로 갱신한다.

## 현재 제한 사항

- 도보 이동 시간은 직선거리 Heuristic이며 NAVER 길찾기, 대중교통, 자동차, 접근성, Turn-by-turn 시간이 아니다.
- 현재 Provider 장소 Adapter는 영업시간이나 비용을 채우지 않으므로 해당 제약조건은 대체로 일부만 확인되거나 알 수 없다.
- 식사 시간 범위는 Provider 예약 데이터가 아니라 카테고리·원본 텍스트 규칙이다.
- 다양성은 Heuristic 효용이며 요청된 카테고리 포함을 강제하는 제약조건이 아니다.
- Greedy 경로는 전역 최적을 보장하지 않으며 학습된 행동 데이터가 없다.
- 명시적인 출발 좌표가 없어 첫 경유지까지의 이동 시간은 0이다.
